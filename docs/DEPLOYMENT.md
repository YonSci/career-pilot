# Deployment: the invite-only beta on Render

Version 0.3 is multi-user. Each account has its own evidence, sources, postings, evaluations, alerts and drafts; members bring their own OpenAI key and connect their own mailbox by IMAP. One always-on Render web service runs the API, the dashboard, the scheduler and the Telegram poller, with SQLite on a persistent disk. That is enough for a cohort of 20 to 50 people; a Postgres and worker split can come later without changing the code.

## One-time setup (about 20 minutes)

1. **Repository.** Push this project to a private GitHub repository. `render.yaml` at the root is a Blueprint that defines the service, its disk and its environment variables.
2. **Render.** Create an account at render.com, choose **New → Blueprint**, pick the repository. Render reads `render.yaml`. Fill the variables marked `sync: false`:
   - `PUBLIC_URL` and `CORS_ORIGINS`: `https://<service-name>.onrender.com` (or your custom domain once attached).
   - `OPENAI_API_KEY`: your key. It is used only by the owner account; members must add their own.
   - `TELEGRAM_BOT_TOKEN`: the beta bot's token (create a second bot in BotFather so your personal instance keeps its own).
   - `RELIEFWEB_APPNAME`: your appname (shared by all accounts; ReliefWeb's terms allow one application).
   - SMTP values only if you want email alerts for members.
   `APP_TOKEN` and `SECRET_KEY` are generated by Render. `SECRET_KEY` encrypts every member's stored API key and mailbox password: back it up from the Render dashboard and never rotate it casually.
3. **Deploy.** Render builds the Docker image (dashboard included) and starts the service. The root URL is the public landing page with a "Request an invite" form (requests appear in the Cohort tab); the app is at `/app/`. Open `/app/` and create the **first account: it becomes the owner** with the Cohort (admin) tab. The sign-up form asks for a setup code: paste `APP_TOKEN` from the service's Environment page (or set `OWNER_EMAIL` beforehand to restrict the owner account to your address).
4. **Custom domain (optional).** Settings → Custom domains; Render issues the certificate. Update `PUBLIC_URL` and `CORS_ORIGINS`.

Cost: the `starter` instance (about 7 USD per month) plus the 2 GB disk (cents). Free instances sleep and stop scheduled searches, so they are not suitable.

## Inviting people

Without a code: while invite-only, `OPEN_SEATS_PER_DAY` people (default 25, counted over the last 24 hours) may join without one. "Request an invite" on the landing page records the request as before and, while a place is open, goes straight to sign-up with the email filled in; an empty code on the sign-up form uses a place too. Once the day's places are taken, requests wait for you as before. Open places show in the Invitations list with the note `open:<email>`. Set `OPEN_SEATS_PER_DAY=0` to go back to codes only, or `INVITE_ONLY=false` for unlimited sign-up. Only the first `SPONSORED_SEATS` members get AI included either way; later members bring their own OpenAI key.

Telegram: Account → Link Telegram shows "Open Telegram and press Start", a `t.me/<bot>?start=CODE` link that links the chat when they press Start, without typing the code. The bot replies to Start from a chat nobody linked with the sign-up link, and to an expired link with how to get a new one; other messages from strangers still get no reply.

With codes: Cohort tab → Invitations → Generate codes. Each code is a link like `https://<host>/app/?invite=CODE` and works once. Send it with the short onboarding note below. The same tab shows the two activation metrics per person: verified CV plus at least one source, and whether they prepared an application.

Onboarding note to send:

> 1. Open the link, create your account. 2. Account → paste an OpenAI API key (platform.openai.com → API keys; you pay only for your own usage, typically 1 to 3 dollars per search of 50 postings). 3. My evidence → upload your CV, verify the facts. 4. Job sources → add the suggested sources, or your mailbox with a JobsFindAI label for LinkedIn alerts. 5. Account → Link Telegram for alerts. 6. Preferences → enable scheduled searches.

## Migrating your personal data (optional)

Your local instance can stay separate. If you prefer one instance, copy `data/career.db` to the Render disk before creating the first account:

```powershell
# local: safe snapshot while running
.venv\Scripts\python -c "import sqlite3; s=sqlite3.connect('data/career.db'); d=sqlite3.connect('career-export.db'); s.backup(d); d.close()"
```

Then upload with Render's shell (Dashboard → Shell) or `render disks` tooling to `/app/data/career.db`, restart, and sign up: the first account claims every record that existed before accounts.

## Backups

Render disks are snapshotted daily for seven days. Additionally, the owner can download a consistent copy at any time from the Render shell:

```bash
python -c "import sqlite3; s=sqlite3.connect('/app/data/career.db'); d=sqlite3.connect('/app/data/backup.db'); s.backup(d); d.close()"
```

Deleting the service or the disk deletes all accounts' data.

## Operations

- Logs: Render dashboard → Logs. Search failures include the source name; evaluation failures back off automatically.
- Scheduled searches run inside the web service; the Render health check keeps it alive.
- `/health` reports the deployed commit (`"commit": "5ff833f"`, from Render's `RENDER_GIT_COMMIT`); compare it with `git log -1 --format=%h origin/main` to confirm a deploy has landed. Outside Render it reads `"local"`.
- Telegram uses long polling; no webhook is needed. If you ever set a webhook, unset it with `deployment/telegram_setup.py polling`.
- CI (`.github/workflows/ci.yml`) runs the backend tests and the dashboard build on every push to `main` and every pull request. Render deploys on push regardless; to deploy only commits that pass, set Render → Settings → Auto-Deploy to **After CI Checks Pass**.
- A rejected OpenAI key, or an OpenAI account with no credit left (`insufficient_quota`), stops a search's evaluations after the first failure with one warning naming who must act. Ordinary rate limits are retried in later searches.
- Shared catalog, phase 1 ([CATALOG_DESIGN.md](CATALOG_DESIGN.md)): postings from ReliefWeb and employer job boards are also stored once under the system account, including postings members' keywords reject. Nothing reads them yet. `python -m career.catalog_report` shows its size, sources, and how many postings several members collect. `CATALOG_ENABLED=false` stops it; postings unseen for 90 days are deleted.
- Shared catalog, phase 2 (starter results): a member with no enabled source of their own searches the catalog's postings seen in the last 7 days and still open, through their keywords, JEV and evaluation budget as usual. Their scheduled searches run once their CV is verified. Members with sources are unchanged. Starter jobs carry `via: catalog`; `catalog_report` counts them. `CATALOG_STARTER=false` turns it off.
- Shared sources (catalog phase 3): Cohort tab → Shared sources adds ReliefWeb searches or employer boards that are read for everyone every `SHARED_FETCH_HOURS` (default 3), even if no member added them; members without sources get their postings as starter results. `CATALOG_SHARED=true` also reads members' ReliefWeb and employer-board sources once for everyone: their searches then skip a source read in the last 3 hours and use all shared postings, which members' keywords screen as usual. Email alerts, RSS, careers pages and Remotive stay per member. Switching it off returns to per-member fetching. `catalog_report` shows shared sources, recent reads and failures; members' sources appear only as counts.
- Retention: once a source has been fetched successfully for 7 days without listing a posting, the posting has left its source. It is no longer offered as a starter result, and members' jobs for it show "No longer listed", are not evaluated and are not alerted. Only postings from catalog sources (ReliefWeb, employer boards) are checked. `catalog_report` shows how many postings have left their source and each source's last successful fetch.
- Job views and filters: Opportunities offers List, Cards (swipe to shortlist or skip) and Map. Filters on work arrangement, level, contract and stated salary use the AI evaluation's posting details, else rules applied to the posting text (`career/posting_facts.py`). The map places each job at the centre of the country its location names (`career/geo.py`, an offline table: no geocoding service sees members' jobs). Map tiles come from OpenStreetMap's tile servers, so a member opening the map sends their IP address and the map area to OpenStreetMap; the job list itself is not sent.
- Keyword-rejected sample (catalog phase 4): each search may store one posting the member's keywords rejected (not excluded keywords or a strict location), up to `KEYWORD_SAMPLE_PER_MONTH` per member (default 10, 0 = off). It is evaluated first, from the same budget, shown as "Outside your keywords", and never alerted. `jev_report` compares the share of good matches (LLM score 60 or more) in this sample with postings the keywords kept; a similar share means keywords are hiding good jobs.
- Scheduled searches are on by default for new members on plans that include them, and start once the member adds a source; accounts without an enabled source are never searched on schedule. `python -m career.schedule_reminder` lists members who have sources but schedules off, with the message they would get; add `--send` to email them (and message them on Telegram if linked). Each member is reminded once.
- Per-user secrets are encrypted with `SECRET_KEY`. Changing it makes stored keys unreadable; members would re-enter them.

## Growing past the beta

- Move to Render Postgres by setting `DATABASE_URL` (SQLAlchemy handles both) and copy records with a short script.
- Add a worker and Redis and set `TASK_QUEUE=celery`; the Celery tasks already run per account.
- Billing: the `plan` field on each account is what Paddle webhooks will set (Free / Pro). Entitlements are enforced from `PLANS` in `backend/career/auth.py`.

## Alternative: Vercel for the dashboard

Not needed for the beta: the API serves the dashboard and sessions are same-origin cookies, which keeps CSRF simple. If the dashboard moves to Vercel later, the API must issue `SameSite=None; Secure` cookies and allow the Vercel origin in `CORS_ORIGINS`.


## Analytics and session replay (PostHog)

Set `POSTHOG_KEY` (the project API key from PostHog → Project settings) on the service; `POSTHOG_HOST` defaults to the EU cloud and `POSTHOG_REPLAY=false` turns replay off while keeping events. Nothing is loaded in the browser until the key is set. The privacy notice already describes the recording and masking.

What is captured: page views, autocaptured clicks, dead clicks, JavaScript exceptions and API errors (`api_error` with path, method and status), and these product events:

| Stage | Events |
|---|---|
| Landing | `landing_page_viewed`, `landing_section_clicked`, `preview_tab_clicked`, `invite_cta_clicked`, `invite_requested`, `invite_request_failed`, `signin_link_clicked` |
| Accounts | `signup_started`, `signup_completed`, `signup_failed`, `login_started`, `login_completed`, `login_failed`, `logout` |
| Evidence | `cv_uploaded` (method, facts, seconds), `profile_completed` (verified_facts) |
| Sources | `job_source_selected` (kind, suggested), `job_source_tested` |
| Search | `job_search_started`, `job_search_completed` (seconds, added, matched, alerts, failed_sources), `job_search_failed` |
| Matching | `match_analysis_started`, `match_analysis_completed` (seconds, score) |
| Jobs | `job_result_opened` (score, source, unread), `job_saved`, `job_skipped`, `job_marked_applied` |
| Applications | `application_created`, `application_ready`, `application_exported` |
| Other | `telegram_link_started`, `assistant_question_asked` |

Suggested funnel in PostHog: `landing_page_viewed` → `signup_completed` → `profile_completed` → `job_search_completed` → `job_result_opened` → `job_saved` → `application_created`. Members are identified by their account ID with plan, role, `has_key`, `sources` and `verified_facts` as person properties; no email or name is sent. Session replay masks all inputs and hides evidence, postings, drafts, names, emails and assistant text.


## Sponsored seats (AI included for early members)

`SPONSORED_SEATS` (default 20) is the number of members who, in registration order, use the server's `OPENAI_API_KEY` instead of bringing their own. They are placed on the **sponsored** plan: 10 sources, 25 evaluations per search, 300 evaluations per month, 5 application packages per month, scheduled searches allowed. When the monthly evaluations are used up, searches still collect postings but stop evaluating until the next month, with a message that explains it. A member who adds their own key is no longer billed to the server key and keeps the sponsored plan's caps unless the owner changes the plan.

The Cohort tab shows a "Sponsored seats" tile with how many evaluations ran on your key this month, and a Sponsor / Unsponsor toggle per member. Rough cost per sponsored member at full usage: 300 evaluations ≈ 6 to 18 USD plus 5 packages ≈ 5 USD per month; most members use far less.


## Security model (summary)

- **Data isolation.** SQLite has no row-level security, so isolation is enforced in the application: every record carries the owning `user_id`, all reads and writes go through scoped helpers (`rows`, `find`, `get_row`, `put`) that filter by the signed-in user, and background jobs enter the user's scope explicitly. Tests assert that one member cannot read or change another member's jobs, applications, sources, alerts or Telegram link.
- **Secrets.** The browser receives only the PostHog project key (public by design) and the app name. Session cookies are HttpOnly. Members' OpenAI keys and mailbox passwords are encrypted at rest with `SECRET_KEY` and never returned by any endpoint. No secrets are committed to the repository (`.env`, `data/` and client JSON files are ignored).
- **Files.** Uploaded CVs are size-limited (5 MB), restricted to DOCX, text PDF, TXT and Markdown, checked for zip bombs, converted to text in memory and not stored as files; only the extracted text is kept in the database. Exports are generated on request. The database lives on the service's persistent disk.
- **Spend controls.** Per plan: evaluations per search, evaluations per month (sponsored), packages per month, sources. Per account: `AI_ACTIONS_PER_HOUR` on manual model-calling actions. Global: `SERVER_KEY_MONTHLY_CALLS` caps every model call charged to the server key (owner and sponsored members), after which such calls stop with a clear message until the next month. Set a matching monthly limit on the OpenAI account as the backstop of last resort. The assistant is limited per IP.
- **Untrusted model input.** Postings, CVs, alert emails and careers pages are data, never instructions: the system prompt states this, inputs are passed as JSON data, control characters are stripped and sizes capped, outputs are schema-constrained, evidence references are validated against the verified facts, URLs must appear in the source text, and drafts pass an independent review.
- **Outbound network.** Sources may only target public addresses, resolved once and pinned for the connection, with redirects re-checked and response sizes capped.
- **Monitoring.** Server-side events to PostHog (`server_search_completed`, `server_search_failed`, `server_application_drafted`, `server_application_failed`, `server_ai_call_failed`, `server_alert_delivery`, `server_key_cap_reached`) plus backend exceptions in error tracking. Infrastructure metrics and uptime come from Render's dashboard and an external check on `/health`.


## Income and promotion (version 0.4)

**Plans and prices.** Free, Pro and Pro Plus, priced in ETB for Ethiopia and USD for cards elsewhere (`PRICE_*` settings). Paid members run on the server's OpenAI key with monthly evaluation caps (600 and 1,500), so keep `SERVER_KEY_MONTHLY_CALLS` and the OpenAI account limit in place. Application-package credits (`package`, `package_5`) work on every plan, including Free.

**Payment routes**, chosen automatically by what is configured:
- **Chapa** (Telebirr, bank cards, ETB): set `CHAPA_SECRET_KEY`; register the webhook `https://<host>/api/billing/webhook/chapa` with a secret hash in `CHAPA_WEBHOOK_SECRET`. The member is sent to Chapa's hosted checkout, the return URL verifies the transaction server-side, and the webhook is the backup.
- **Lemon Squeezy** (cards worldwide, USD, merchant of record): create one product per plan and one for packages, paste the hosted checkout links into `LEMON_CHECKOUT_PRO`, `LEMON_CHECKOUT_PRO_PLUS`, `LEMON_CHECKOUT_PACKAGE`, and register the webhook `https://<host>/api/billing/webhook/lemonsqueezy` (events `order_created` and `subscription_payment_success`) with `LEMON_WEBHOOK_SECRET`. The checkout link carries the payment reference in custom data.
- **Manual** (always available): with no gateway, choosing a plan sends the owner an email and shows the member `BILLING_CONTACT` (a Telebirr number or bank details) with a reference. The owner confirms in the Cohort tab under "Payments awaiting confirmation" and the purchase activates immediately.

Purchases are system records; applying one is idempotent; a month stacks on a running month; lapsed plans return to what the member had (checked by the scheduler).

**Employers.** The landing page's employer form (`/api/employers/post`) creates a pending request and emails the owner. Approving it in the Cohort tab features it for 14 days at the top of the public listings, in the sector pages and in the Telegram digest; rejecting removes it. Price in `FEATURED_LISTING_ETB` / `_USD`.

**Institutions.** The enquiry form (`/api/institutions/enquiry`) emails the owner and lists in the Cohort tab. Seats are priced by `INSTITUTION_SEAT_ETB` / `_USD`; members of an institution get the Organisation field set for group analytics.

**Referrals.** Every member has three personal invitation links under Account; sign-ups through them are attributed (`referred_by`) and counted in the Cohort tab.

**Testimonials.** Added by the owner in the Cohort tab; the landing page's testimonials section appears as soon as one exists (server-rendered).

**Telegram channel.** Create a public channel, add the bot as an administrator, set `TELEGRAM_CHANNEL_ID` (for example `@jobsfindai`). The bot posts new field-relevant roles daily at `TELEGRAM_CHANNEL_DAILY_HOUR` UTC and a closing-soon digest on Mondays, each linking to the public listings with UTM tags. The Cohort tab has "post now" buttons.

**Search traffic.** `/jobs` and `/jobs/<sector>` (data-science, climate, gis-remote-sensing, agriculture, mel, development) are server-rendered, indexable pages with JobPosting structured data; `/sitemap.xml` and `/robots.txt` are served by the app.


## Public site and installable app (version 0.4.1)

**Public pages**, all server-rendered from the public listings and refreshed every ten minutes: `/jobs` (search box, field, location, employer and closing-date filters, 24 per page), `/jobs/<sector>`, `/job/<slug>` (one page per posting with key facts, salary and contract when stated, apply link, share buttons for Telegram, WhatsApp, LinkedIn and email, similar roles, JobPosting structured data), `/organisations` and `/organisations/<slug>`, `/guide` and `/guide/<slug>` (five articles in `career/guide.py`). The Telegram digest links to `/job/<slug>` so channel readers land on the site. `/sitemap.xml` lists everything.

**Installable app.** `public/manifest.webmanifest`, `public/sw.js` and `public/icons/` ship with the dashboard build under `/app/`. The service worker caches only static assets and the app shell; API calls are never cached. Members see "Install app" under Account (Chrome and Edge prompt; iPhone uses Share → Add to Home Screen).

**Push notifications.** Generate a key pair once with `python deployment/vapid_keys.py` and set `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` (a `mailto:` address). Members enable push per device under Account; subscriptions are stored encrypted with the member's other secrets (up to five devices). "push" is then an alert channel like Telegram and email, with a test button under Preferences. Subscriptions the push service reports as gone (404/410) are dropped automatically.

## JEV ranking before LLM evaluation

JEV (TypeSafe AI, `career/jev.py`) gives each posting a cheap relevance score so the LLM spends its evaluations on the most promising ones. It rates experience, skills, domain, seniority, location and preferences (weights 30/25/20/10/10/5, the same rubric the LLM is told to apply) from verified facts only; contact facts and posting URLs are not sent. The score ranks postings: it is not an eligibility check, and only LLM-evaluated matches are ever alerted.

1. **Shadow.** Set `TYPESAFE_API_KEY`; `JEV_MODE` is `shadow` in `render.yaml`. Searches store a `jev` score on each posting and change nothing else. Each run records `jev: {scored, cached, failed, held, sampled, tokens}`. In every search, `JEV_SAMPLE_SHARE` (0.1) of the LLM evaluations, rounded down, goes to a random sample of postings rank mode would hold; they are marked `sample` on their JEV score. The sample shows how many good matches JEV would miss, which postings evaluated in the normal queue cannot.
2. **Compare.** After a few days of searches, run `python -m career.jev_report` in the Render Shell. It uses the same routing rule as rank mode and prints: how many of all JEV-scored postings rank mode would send to the LLM; the rank correlation with LLM scores and how many LLM-strong and saved/applied postings would have been kept (over postings evaluated in the normal queue, with 95% intervals); the good matches found in the random sample, with an estimate of how many held postings are good; and a sweep of cutoffs from 20 to 40 showing, for each, the share of all scored and of evaluated postings sent to the LLM and of good matches (LLM score 60 or more) kept. Switch only when the LLM-strong and saved/applied shares are both at least 95% and the sample finds few good matches; adjust `JEV_MIN_SCORE` (default 40) and `JEV_CONFIDENT` (default 0.6) if not. With small samples the intervals stay wide: 20 of 20 kept still only shows at least 84%.
3. **Rank.** Set `JEV_MODE=rank`, optionally for a few accounts first with `JEV_ACCOUNTS` (comma-separated emails). The LLM then evaluates postings in JEV order and skips those scoring below `JEV_MIN_SCORE` with at least `JEV_CONFIDENT` confidence. Uncertain low scores and manually added postings are still evaluated; skipped postings stay listed and can be evaluated by hand.

JEV runs only for accounts with LLM evaluation available and remaining budget, scores at most `JEV_MAX_PER_RUN` (300) postings without a current score per search, highest keyword priority first, with `JEV_WORKERS` (8) in parallel, and reuses a score until the posting, verified evidence, matching preferences, model or rubric change. If JEV fails, postings keep their keyword order; if the first calls all fail, the rest of that search's scoring is skipped. JEV does not count against members' monthly evaluations. `JEV_SHOW` decides who sees JEV scores in the dashboard (a preliminary score on unevaluated postings and a six-dimension breakdown on each posting): `owner` (default, the admin only), `all`, or `off`. Show them to members only after the cutoff sweep on rubric 2 looks sound. `JEV_MONTHLY_TOKENS` (default 20,000,000 input tokens, all accounts together, 0 for no cap) is a hard monthly cap: once it is reached, postings keep keyword order until the next month. The report prints this month's use; set a matching limit with TypeSafe.

**Rubric and model changes.** Each score records the rubric version and the dated model that answered. Pin `JEV_MODEL` to a dated name from `python -m career.jev_report --models` so a provider update to `jev-latest` cannot mix old and new scores. Changing the rubric (`RUBRIC_VERSION` in `career/jev.py`) or `JEV_MODEL` rescores postings as searches next rank them; the report compares only current-rubric scores. Postings the LLM already evaluated are not ranked again, so run `python -m career.jev_backfill` (200 postings; pass a number for more) to rescore them and restore the comparison data. Rubric 2 separates contradicted requirements from requirements the evidence does not mention, so scores and good cutoffs differ from rubric 1: run the cutoff sweep again before choosing `JEV_MIN_SCORE`.
